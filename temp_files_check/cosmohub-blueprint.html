The model we're following

Structure is the product. Content sits on top.

Palantir's Gotham does not compete on interface — it competes on the Ontology, a layer that unifies data from every available source into objects, properties, and links representing real entities and how they connect. Every application — Graph, Gaia, Dossier — reads from that same layer.

CosmoHub follows the same discipline. The tracks, the ticker, the dashboard — none of them are the product. The product is a continuously enriched graph of the space talent and research ecosystem. Build the graph correctly, and every application becomes easier to ship, not harder.

Application layer

Six tools. One shared graph underneath.

None of these own their own data. They are views and actions over the ontology — exactly how Gotham's Graph and Gaia apps work.

APP/01CORE

Graph Explorer

Whiteboard-style link analysis — trace how a person, institute, or mission connects to everything else in the ecosystem.

APP/02MATCHING

Fellowship Match

Surfaces openings a person's profile actually qualifies for, computed from tracked skills and activity.

APP/03PARTNER-FACING

Institute Radar

Gives partner institutes a live view of qualified, engaged talent active in their research area.

APP/04GEOSPATIAL

Mission Tracker

A timeline and map view of active and upcoming missions, tied back to operating institutes.

APP/05SIGNAL

Research Index

Live momentum on tracks and topics, computed from real publication and enrollment velocity.

APP/06STRATEGY

Skill Gap Analyzer

Compares mission and company skill demand against the talent pool — informs which track to build next.

Insider workflow

How we onboard a new data source.

Every source — a new institute, a new fellowship board, a new research feed — follows this same path.

01

Identify the source

Confirm what entities it contains and which existing object types they map to — or whether a new object type is needed.

02

Write the parser

Build a connector that extracts entities and relationships from the source's native format into a structured intermediate form.

03

Map to the ontology

Match extracted fields to object properties and links. Reuse existing types wherever possible — extend the ontology deliberately, not by accident.

04

QA against the graph

Check for duplicate entities, broken links, and property mismatches before anything reaches production.

05

Promote to production

Once verified, the mapped data becomes queryable by every application — Graph Explorer, Fellowship Match, and everything built after them.

Ten-year build

From core ontology to the reference layer for the space economy.

YEAR 1

Foundation

  • Core ontology live: Person, Institute, Track, Fellowship
  • First tracks published
  • Landing page + profile system
  • Manual ingestion from initial partner institutes
YEARS 2–3

Integration

  • Automated parsers for research feeds and fellowship boards
  • Fellowship Match and Institute Radar shipped
  • First paid institute partnerships
YEARS 4–6

Intelligence

  • Graph Explorer and full analytics suite live
  • Mission and Company objects added
  • Direct hiring partnerships with aerospace companies
  • Expansion into a global institute network
YEARS 7–10

Standard

  • Reference layer for the global space talent ecosystem
  • Ontology and analytics licensed to institutes and agencies
  • AI-assisted research and fellowship matching
  • Space policy and space-law tracking integrated
Building the team

The roles that grow the ontology.

Content roles matter, but the roles below are what compound the platform's value — they're the ones to prioritize first.

ONTOLOGY DESIGN

Defines and evolves object types, properties, and links as the platform grows. Owns schema decisions.

DATA INTEGRATION

Builds parsers and connectors for new sources — institutes, research feeds, fellowship boards, mission databases.

APPLICATION DEV

Builds the user-facing tools that read from the ontology: Graph Explorer, Fellowship Match, and what comes after them.

INSTITUTE PARTNERSHIPS

Onboards institutes as both data sources and consumers of the graph — the channel that keeps the ontology fed.

TRACK & CONTENT DESIGN

Builds the learning tracks that sit on top of the ontology — not instead of it.
